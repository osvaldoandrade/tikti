Strict Isolation

Context-aware tokens. No access token is issued without a valid tid (Tenant ID) and verified membership. Prevents horizontal privilege escalation by design.

// 02 Token Exchange

Identity Swapping

Exchange high-friction Identity Tokens (HS256) for service-scoped Access Tokens (RS256). Ideal for autonomous agents requiring specific scopes.

// 03 Verification

Cryptographic Audit

Public JWKS endpoints allow offline validation by any resource server. Zero shared secrets between microservices.

System Specifications & FAQ

Why separate Identity Tokens from Access Tokens?

The Tradeoff: Monolithic identity providers force you to choose between performance (symmetric keys) and security (asymmetric keys). HS256 is fast but requires sharing secrets. RS256 is secure for distributed systems but computationally heavier for high-frequency logins.

The TIKTI Approach: We use HS256 for the initial Identity Token (internal session) to maintain millisecond latency during login. We then exchange this for a scoped Access Token (RS256) for downstream services. This allows Resource Servers to validate tokens offline using cached JWKS without ever possessing a secret key.

How does TIKTI handle high-throughput persistence without massive RAM?

TIKTI is designed for scenarios where O(1) lookups are non-negotiable. Relational databases introduce latency with complex joins, while pure Redis is limited by expensive RAM.

Solution: We use KVRocks. It implements the Redis protocol but stores data on NVMe SSDs via RocksDB. This allows TIKTI to store millions of user sessions with a minimal RAM footprint while maintaining sub-millisecond access times and full durability.

How do I deploy this to production?

TIKTI is Cloud Native by design. The application tier is stateless and scales horizontally via standard Kubernetes HPA.

We provide a standard Helm chart that provisions the TIKTI deployment, the KVRocks StatefulSet (with persistent volume claims), and exposes the JWKS endpoint via Ingress. Run helm install tikti ./charts/tikti to deploy a fully HA cluster.

Does TIKTI lock me into a proprietary SDK?

No. TIKTI implements a pragmatic subset of OIDC/OAuth2 standards tailored for service-to-service communication.

It uses standard JWTs with compliant claims (`iss`, `sub`, `aud`, `exp`, `iat`). Any library compatible with RS256 signing and JWKS discovery (e.g., `node-jsonwebtoken`, Go's `jwt-go`, Python's `PyJWT`) works out of the box.

How do I trace authentication failures in a distributed system?

Observability is built-in. Every decision is logged structurally.

TIKTI emits JSON logs for Auth Failures (incorrect passwords, invalid signatures), Token Exchanges, and Tenant Operations. These logs include the correlationId, tenantId, and actorId, making them ready for ingestion by SIEMs like Splunk or Datadog for immediate root-cause analysis.
